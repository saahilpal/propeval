# ADR-006: Open-Source Build-vs-Adopt Strategy (Transparent Core + Mature Primitives)

**Status:** Accepted | **Date:** 2026-11-19

* **Decision:** **Adopt** mature, permissively licensed primitives—OpenTelemetry SDK (`1.45.2`), SciPy (`1.18.1`), statsmodels (`0.15.0`), Hypothesis (`6.170.15`), Microsoft Presidio, PostgreSQL `17.12`, Valkey `8.x` (BSD-3-Clause, Phase 2 multi-pod), and official LLM SDKs (`openai 3.54.0`, `google-genai 3.2.0`, `groq 1.7.0`)—while **building custom** (~1,800–2,500 LOC across clean domain modules) the async eval runner, Hybrid FSM+LLM simulator, Indian real-estate oracles, calibrated rubric judge, and paired statistical engine. Integrate Langfuse v4 / MLflow 3.18 strictly via OTLP export.
* **Requirement:** Satisfies FR-05–FR-14 (stateful Hinglish FSM simulation, domain-specific grading, paired statistical rigor), NFR-12 (reproducibility), NFR-16 (OTel conformance), and commercial license hygiene.
* **Alternatives:** (1) **Adopt DeepEval (`4.3.4`) or Ragas (`0.4.4`)** as core eval engine; (2) **Adopt Promptfoo (`0.125.1`)** as core runner; (3) **Adopt Langfuse (`v4.81.0`)** as core backend; (4) **Adopt LiteLLM (`1.110.0`)** as mandatory model router; (5) **Use Redis (`8.10.1`)** directly.
* **How the alternatives work:** DeepEval and Promptfoo both support custom transparent judge prompts and deterministic assertions, wrapped inside pytest/Node.js test runners. Ragas provides RAG-specific metrics. Langfuse v4 runs an OTel + ClickHouse + Postgres + Next.js observability platform. LiteLLM proxies 100+ providers.
* **Selection reasoning:** While DeepEval and Promptfoo allow custom judges, neither natively solves PropEval's core differentiators: **stateful Hybrid FSM+LLM Hinglish simulation with replayable mock real-estate tools, per-call crash-safe USD budget reservations, and paired multi-trial statistical gating (Wilcoxon + two-stage cluster bootstrap + clamped Rogan–Gladen)**. Furthermore, Promptfoo's Node.js runtime clashes with Python/SciPy async workers; Ragas (`0.4.4`) carries pre-1.0 churn; Langfuse v4 requires ClickHouse ops and `ee/LICENSE` boundaries; LiteLLM has MIT/Enterprise ambiguity ([Issue #34241](https://github.com/BerriAI/litellm/issues/34241)); and Redis `8.10.1` uses RSALv2/SSPLv1/AGPLv3 whereas Valkey is BSD-3-Clause. Conversely, reinventing OTel, SciPy, or Presidio would be indefensible waste.
* **Rejected alternatives:** Adopting heavy opinionated AI frameworks adds runtime/licensing friction while still forcing us to write the FSM simulator, paired stats engine, and Indian real-estate oracles from scratch.
* **Trade-offs:** We gain 100% control over ledger-first cost accounting, prompt auditability, clean MIT/Apache/BSD licensing, and zero abstraction lag on official SDKs. We accept maintaining ~1,800–2,500 LOC of core Python modules and 3 thin provider adapters (~50 LOC each), and forgo Promptfoo's built-in generic red-team plugin catalog (available via optional CLI adapter).
* **Failure modes:** Official provider SDK breaking changes (mitigated by pinning major versions behind `LLMProvider` Protocol); scope creep into building a generic APM UI (prevented by exporting OTLP to Grafana/Langfuse).
* **Cost:** ~2–3 weeks of focused Python engineering for the custom core; substantially lower long-term debugging and dependency-upgrade overhead.
* **Revisit conditions:** Adopt `pydantic-ai-slim` (`2.70.0`, MIT) if PropEval needs >6 LLM providers with uniform structured-output retries; wrap DSPy (`3.5.0`, MIT) later strictly as an optional "Auto-Optimize Prompt" worker.
